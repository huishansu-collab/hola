# 从需求到交互时序

## 任务边界

从目标拆出必要子任务。每项写输入、前置结果、操作、输出、成功条件；只展开一条主路径，按需备注失败或变更策略。保持案例精干，不为凑训练标签安排无意义打断。

涉及“公司”“家”等地点时，区分记忆地址、实时定位、地点匹配和可执行的目的地/上车点。依赖真实输入的匹配在读取完成后开始；独立读取可并行。当前位置相符不能自动推断已确认某个出口。

工具调用、参数和返回值为模拟数据时，在 Case 说明与数据约束标记 simulated。预订、展示、支付、出票为不同状态。用户口头同意不等于支付，用户在站内点击支付卡片记录为用户控制；站外核对和支付动作不放入用户控制，支付平台回传属于外部状态。AI 不自动支付。

## 下单意图与能力准备

识别通用任务、品牌约束和具体商品三个维度。例如任务是饮品下单，品牌是瑞幸，商品仍以用户明确指定的茉莉花奶茶为准；不因将任务归类为订咖啡而改变商品。

下单前检查所需信息和执行能力。输入齐备且彼此独立的准备工作可并行：

- `location.current()`获取当前位置。
- `memory.get(coffee_preferences_key)`读取相关偏好；其他品类使用相应表意变量，不机械查询咖啡偏好。
- `mcps.search(luckin_ordering_capability_query)`发现支持目标品牌下单的MCP服务或工具。

需要匹配收货地点时，另行`memory.get(user_frequent_addresses_key)`，取得保存地址后使用`location.match(current_location, user_frequent_addresses)`。偏好为空时如实返回，不编造习惯；当前明确要求优先于记忆偏好。已有明确且有效的准备信息可复用，记录来源，不为填工具轨道重复查询。

能力发现应返回候选服务、支持范围及已知连接与授权状态。不能直接假设存在支持目标品牌的报价、建单能力。发现结果返回、完成必要判断并满足跨轨道400 ms窗口后，才可调用匹配业务工具；后续调用关联所选服务标识，保存发现→选择→执行的依赖。

能力发现不是授权或下单。状态未知、未连接或未授权时不能视为可执行；按实际结果补齐条件或如实停在待处理状态，不编造成功。Case模拟须明确标记，真实执行映射到实际可用接口。

## 按信息缺口回答

用户已经明确给出的事实、目标和约束，作为共享上下文。助手优先补足当前缺少的信息；不为了让句子显得完整，再解释用户已经给出的前提。确需纠错、消除歧义或区分候选项时才补充相关解释。用户转而询问释义时仍应回答，不能机械删除所需信息。

例如用户问“流浪汉的英文怎么拼，V 开头”，回答候选词和字母拼写即可，不再追加“意思是流浪汉”。追问近义词时重点补充不同词的语气和适用场景。语音给直接答案与必要差别，卡片承载便于扫读的完整结果；避免逐项朗读卡片全部字段。

## 查询与结果卡片

查字典、查汉字读音、解释字义、词语释义、拼写、造句等，模型凭已有知识即可可靠回答的问题，直接回答，不为补齐工具轨道而安排工具调用。

- 不虚构`dictionary.search()`等不存在的工具，也不将其作为模拟工具加入Case。
- 仅在需要实时信息、外部资料、用户私有数据，或需要核实不确定内容时，使用实际可用的工具；Case中的模拟请求与响应也必须对应已确认存在的能力，不因缺少接口而发明查询工具。
- 是否展示结果卡片独立判断；展示卡片不意味着必须先调用查询工具。仅展示卡片时只记录实际展示动作，不伪造查询来源。
- 未使用工具时，工具轨道保持为空，不添加占位事件。

本规则替代此前“所有信息查询型Case都必须安排查询工具”的要求。下述查询闭环仅适用于确实调用外部查询工具的情况；TTS、ASR等制作工具不记为Case业务工具。

按“查询请求 → 查询返回 → 展示/更新卡片与口头回答并行”组织依赖；只有回答确实依赖可见界面时才等待卡片。基于结果的卡片和答案不能早于查询返回。追问需要新增查询时，追加工具请求并更新相应卡片，保留结果和卡片之间的关联。

查询与卡片展示均记录请求/返回 Events，分别映射工具调用轨道的 tool clip；static_context.tools 提供对应参数 schema，tool_dependencies 记录真实依赖。卡片展示是助手调用工具的动作，不归入用户控制。只有用户实际点击时才添加用户控制事件。

卡片不能只写“显示结果”：在展示工具参数中保存 card_id、卡片类型、标题和结构化内容；内容来自实际查询结果时保存 source_event_id，直接回答生成的卡片不伪造查询事件ID，在返回中保存卡片状态。词汇卡可突出单词、逐字母拼写、简短释义；近义词卡突出词语和用法差别。字段按查询内容选择，不编造真实来源链接。脚本预览直接呈现用户能看懂的卡片内容。

区分 Case 中模拟的屏幕行为与制作平台实际渲染能力。只在工具轨道和 JSON 记录展示事件，不能宣称平台已渲染可见卡片；用户要求实际界面预览时，还需完成对应渲染或明确交付边界。

### 文字学习场景的专用卡片

查询工具按信息来源决定，展示工具按内容形式决定。“无需查询”不等于“无需卡片”。涉及汉字辨认、读音、拼写、字词释义、造句及近义词对比时，默认调用 `ui.show_card` 展示文字学习专用卡片，使字形、拼音、例句和对比内容可见。

- 已有知识足以可靠回答时直接组织卡片与答案，不添加查询工具，不伪造查询事件或 `source_event_id`；实际需要外部核实时才追加相应查询。
- 识字卡突出字形、读音和简短用法；拼写卡突出完整词形及必要字母顺序；造句时更新例句；近义词卡展示词语与用法差异。同一学习对象优先更新原 `card_id`，保留相关上下文。
- 专用卡片通过现有 `ui.show_card` 的 `card_type` 与结构化 `content` 表达，字段以项目实际契约为准，不新增虚构的专用查询或卡片工具。记录展示请求、返回及工具轨道片段。
- 语音回答与卡片展示可并行；若台词要求用户看卡片，则在卡片展示完成后满足规定的跨轨道依赖间隔再说。
- 用户打断时停止旧解释，依据听完后的最新问题更新卡片，不把已丢弃的后文加入新卡片。原有已展示内容不冒充已撤销。
- 用户明确只要语音、无需卡片，或设备不支持屏幕时，遵循该限制并在场景说明中记录；不为此伪造展示成功。

例如“言字旁加吉念什么→帮我造句→打断追问同义词”：展示识字卡，造句时更新例句，听完追问后更新近义词对照。可不调用任何查询工具，但仍有 `ui.show_card` 调用。

## 按实际依赖并行安排语音与工具

助手语音与工具执行可以在时间线上重叠，不默认安排成“工具全部完成 → 助手开始说话”的线性流程。

- 回答所需信息已经可用且满足前置片段结束后至少400 ms的窗口时，及时开始回答。卡片格式化、渲染、更新等操作可与语音并行，无需等待界面展示完成。
- 回答依赖尚未返回的结果时，等待对应结果。等待期间可以进行必要的澄清或简短承接，但不能提前播报未知结果或宣称执行成功。
- 台词引用可见界面时，等待对应内容显示。例如“屏幕上这三个词”的起说时刻，应在卡片展示片段结束后至少400 ms；只讲解词语本身则不受此限制。
- 按片段判断依赖。一段回答只有后半句依赖工具时，可以先说已有依据的前半句，不必阻塞整段回答；后半句实际起说前仍须取得依赖结果并满足至少400 ms的跨轨道窗口。
- 各轨道保持独立的真实时长。工具按执行窗口安排，语音按实际音频对齐；不为了视觉整齐强行串行，也不为制造重叠压缩工具耗时。并行不改变助手起声的 400 ms 决策网格和用户结束后的回应间隔要求。

外部查询示例：天气查询工具在14.4秒结束，助手最早14.8秒开始播报天气，卡片可同时于14.8–16.0秒格式化和渲染。两者共同依赖查询结果，语音不依赖卡片完成。示例时间为模拟安排，不是实测延迟。

## 工具执行时间窗口

以下范围是 Case 编排的模拟预算，单位为秒，不是服务性能实测值。按任务复杂度选择窗口内的合理值，不统一压成一个 400 ms 块；有实际日志时优先采用实测并注明来源。

计时从意图已明确、必要输入齐备、可以开始执行算起，到结果可使用或界面变化实际可见为止，包含必要的参数整理、调用、执行和结果处理。用户尚未说完、补充信息、选择或支付所用时间另计。若参数整理单独放在后台判断轨道，应计入整体动作预算，不能在工具执行中重复计算或把整理时间冒充网络耗时。

| 类别 | 常规窗口 | 较慢情况 |
| --- | --- | --- |
| UI 新卡片：格式化、组装、渲染可见 | 1–2 | 2–4 |
| UI 已有卡片内容或状态更新 | 0.8–1.5 | 1.5–3 |
| 本地状态读取：时间、音量、电量、网络状态 | 0.2–0.6 | 0.6–1.2 |
| 本地数据查询：联系人、设备设置、本地索引 | 0.3–1 | 1–2 |
| Memory 精确读取：偏好、地址等已存字段 | 0.3–1 | 1–2 |
| Memory 语义检索与筛选 | 0.8–2.5 | 2.5–5 |
| Memory 写入或更新 | 0.5–1.5 | 1.5–3 |
| 简单网络查询：天气、汇率、订单状态 | 0.8–2.5 | 2.5–5 |
| 复杂业务查询：航班、酒店、库存、多条件筛选 | 2–5 | 5–10 |
| 网络搜索：返回候选结果 | 1.5–4 | 4–8 |
| 搜索结果阅读：单页打开、提取正文或字段 | 1–3 | 3–6 |
| 多来源搜索、阅读与整理 | 4–10 | 10–20 |
| 地点搜索：商家、地址、附近地点 | 1–3 | 3–6 |
| 路线计算：距离、预计到达时间、路线选项 | 1–3 | 3–6 |
| 手机屏幕获取与识别可操作对象 | 0.5–1.5 | 1.5–3 |
| 手机单步操作：点击、滑动、返回及确认变化 | 0.5–1.5 | 1.5–3 |
| 手机短文本输入：聚焦、输入及确认 | 0.8–2 | 2–4 |
| 打开或切换 App，等待可操作 | 1–3 | 冷启动 3–6 |
| 手机多步操作：跨页面查找、选择、填写 | 3–10 | 10–20 |
| 业务写入：日程、表单、任务保存 | 1–3 | 3–6 |
| 通用异步任务提交并取得任务 ID | 0.8–2 | 2–4 |

新卡片从开始格式化到实际显示至少安排约 1 秒；采用 400 ms 决策网格时可用 1.2 秒。已有卡片轻量更新使用对应窗口，不按新卡片完整构建处理。

查询、搜索结果阅读、卡片展示分别计时；复合任务的总预算与其子步骤预算不能重复累计。有依赖就串行，独立动作可并行并按实际关键路径计算。手机跨页面任务按真实步骤和加载等待展开。结果可用后，回答与卡片格式化可并行；台词引用“屏幕上这个”时，卡片必须已显示。

工具返回和真实完成时刻不强制对齐 400 ms；助手下一次决策按网格安排。低于 400 ms 的真实事件保留原时刻，不为了满足最小可视块而伪造执行耗时。

## 异步业务的受理边界

外卖、购物以[支付确认规则](payment.md)为优先例外：包含支付卡片、用户点击、支付回调及支付后订单状态查询，反馈接单／确认或待确认状态。下文平台受理仍是阶段节点，不再是此类 Case 的最终结束点；商家接单查询属于允许范围。其他业务保持下述边界。

业务 Case 仅覆盖“用户首次提出需求 → 补齐必要信息 → 提交执行 → 系统受理并返回凭证”。请求接受后可展示受理卡片并口头反馈，但不延伸到后续履约。以下是对应业务的提交至受理窗口，替代通用异步提交预算，不与其相加：

| 业务 | Case 业务结束节点 | 执行至受理窗口（秒） |
| --- | --- | --- |
| 打车 | 叫车订单已派出 | 1–3 |
| 餐厅订位／订餐 | 预约请求已受理 | 2–8 |
| 点外卖 | 订单提交成功、平台已受理 | 1–5 |
| 订酒店 | 预订请求已受理、返回订单号 | 2–10 |

除上述外卖／购物例外外，司机接单或到达、商家接单、备餐、配送、酒店后续确认均不进入当前 Case；不安排分钟级等待，不通过时间压缩伪造履约完成。助手和卡片使用“已提交／已受理／已派单”等与返回状态一致的表述，不能把受理写成酒店已确认、司机已接单或服务已完成。

若受理接口超时或失败，保留“提交中／受理待确认／失败”的真实或模拟返回状态，不为了结束 Case 编造成功凭证。必要支付、授权等前置条件遵循任务事实，用户操作时间单独记录，不计入受理窗口。

## 400 ms 与流式输出

400 ms为微轮次决策步长。所有非人工输入片段（助手、后台判断、工具调用、表达控制、世界信号）的开始时间必须为400 ms整数倍；人工语音和用户点击保留实际发生时间。语音实际末端和工具执行时长不为凑网格拉伸或压缩。外部真实日志保留原始时间，若与编排网格不同，另存原始来源时间并标明模拟编排，不能冒充实测。

有前后依赖的跨轨道片段，必须满足 `后续开始 >= 前置结束 + 400 ms`。对非人工后续片段，起点取 `ceil((前置结束 + 400) / 400) * 400`。前置后台判断本身持续400 ms不等于已经让出窗口；相同起点或首尾相接均不合格。覆盖用户输入→判断、判断→工具、工具结果→判断或播报、世界回调→判断、卡片→点击等真实依赖。按整条依赖链逐边检查；无相互依赖的动作仍可并行。不要给用户打断等非依赖外部输入强加因果关系。

示例：支付回调35.6–36.0秒 → 后台判断36.4–36.8秒 → 查询工具37.2秒开始。相同状态可合并为长块；不能为了画块改写音频末端。

按时间推进：读取已到达输入 → 更新当前意图和在途任务 → 决定继续听、出声、停播、调用或展示。后续用户台词可供制作规划，但不能进入更早时刻的模型上下文。已生成或已播出的内容与尚未产生的后续内容分开。七轨中不添加回复计划、回复修订或独立播报控制。

连续用户句保持一条 Utterance，句中暂停不切成多个片段。助手正常接话默认在用户结束后至少 400 ms 起声；真实同时说话研究需要明确说明，不能用例外掩盖错误。长台词按自然音频长度延长时间线。

## 打断与最新意图

只有用户起声时助手仍有实际有声信号，才标语音打断；工具执行中的用户改口单独处理。记录用户起声、检测、停播指令、淡出起点、实际停声；实际停声等于助手 Utterance 末端。生产响应延迟只有真实运行日志可证明。

停止说话后继续听取完整意图。能够继续复用的工具请求保留；返回时按最新约束筛选。参数已改时不播报旧成功结果；取消或更新任务依赖当前工具能力。

未播出的文本留在 interruption 的 discarded_text，必要时显示 `[丢弃：文本]`；不进入实际音轨、Utterances 或已发生的历史轮。淡出只作用于真实播出尾段，界面沿用尾部曲线，不添加整块渐变。

## 任务等待期间的表达策略

等待策略按“用户请求结束，到下一次实质性回答之间的连续等待”评估，覆盖多个工具组成的串行、并行及混合依赖链，不只看单个工具耗时。计算实际阻塞路径：串行步骤及后台判断、400 ms微轮次窗口计入等待；重叠的并行耗时不重复累计。工具切换不会重置等待计时。

- 约1秒的短等待：正常等待即可，无需额外处理。
- 整体等待达到约2秒或更长：普通语音场景应安排简短自然的垫话，适合时局部慢说。即使每个工具都很快，也不能忽略依赖链累积形成的长时间沉默。优先及时承接，不等工具全部结束才出声。
- 先启动已具备输入的任务；承接语与后台工具执行并行，不为说垫话推迟工具，也不把垫话误设为依赖工具结果。仍需遵守已有真实依赖的400 ms间隔；独立分支不强行串行。
- 等待较长时，可在简短承接后按场景使用Loading；不为了填满等待刻意拖音、循环“嗯”或反复垫话。已有承接不要求每个工具重复一次，部分等待可安静留白。
- 会议场景或用户耳语不自动等于助手静默，可按已确认音色轻声承接。明确要求静默或已进入纯文字模式时不播报，遵循对应规则。等待用户操作及支付外部回调仍按payment.md处理，不要求反复催促支付。
- 有实质结果且满足依赖窗口时及时回答。垫话不能提前透露未知结果或声称任务成功；在自然语义边界结束承接，转入结果回答。
- 垫话和慢说分别在表达控制轨道标记，关联助手实际语音；同一片段可同时标记，重叠标签分lane。慢说仅作用于指定片段，随后恢复正常语速。“垫话”使用数据契约中的“垫句”标签。

示例：读取记忆、实时定位、地点匹配和商品报价各自较短，但连同判断及微轮次形成约8秒等待。助手先轻声“嗯……”，接“好的，你稍等一下，我来弄一下”，局部慢说；后台持续执行。取得结果并满足依赖窗口后再说“一杯……，送到公司，对吧？”。示例时长为模拟编排，不要求把承接语拉满8秒。

每次新增、删除、串并行调整工具或修改400 ms决策时序，以及实际音频对齐后，都必须重新计算连续等待与最长未承接的沉默区间，复查表达策略。不能只通过依赖间隔校验，就沿用旧的安静等待决定。

### Loading 音效

使用 audio.play('loading') 启动，使用 audio.stop() 停止；这是行为示意，实际参数遵循项目工具契约，停止操作必须关联对应播放实例。

- 播放与停止均记录请求和返回，在工具调用轨道体现，保存实际播放区间、音量与循环范围；不把音效当作助手对白。每个 audio.stop 必须与同一 Case 中前面已出现并启动的 audio.play 配对，关联同一播放实例，按先 play 后 stop 排列；禁止单独出现 stop。
- 3 秒等数值是预计播放时长，不是必须播满的固定时长。任务提前完成或失败时及时停止，再反馈结果。
- 助手承接语结束后再播放；Loading 与助手前后语音至少间隔 400 ms，不重叠。语音与工具可以并行的规则不覆盖这一音效间隔要求。
- 播放期间持续接收用户输入。用户开口时压低音量，明确要求停止时停止播放。
- 悄悄话模式下不播放 Loading，也不使用有声垫话或慢说。
- 使用真实音效资产，遵循当前平台与打包适配边界；不能只写工具事件却缺少可播放音效，并宣称完整交付。

示例一：用户问“今天天气多少度？”，天气查询预计约 2 秒。先启动查询，助手说“嗯……你稍等”，标记垫句和慢说；结果可用后自然接入回答。

示例二：用户说“帮我查一下过去 3 天所有关于苹果的股票价格”。先启动查询，助手说“好的，稍等”。承接语结束并留出间隔后调用 audio.play('loading')，预计播放约 3 秒；结果可用时调用 audio.stop()，留出间隔后回答并展示结果卡片。

## 世界信号：进入悄悄话模式

### 触发与持续

用户轻触Living Edge两下，产生`living_edge.double_tap`世界信号，激活悄悄话模式。该动作记录在Events和世界轨道，不作为助手工具调用或屏幕点击。模式持续生效，直到明确退出；不默认再次双击就是退出。

### 输入与输出

用户仍可通过whisper耳语提出请求，保留真实用户音频。助手继续理解请求、读取记忆、调用工具、展示卡片，但所有回复仅显示文字。用户使用耳语本身不代表进入该模式，必须有明确的模式触发信号。

### 声音与等待

模式生效后，助手不生成或播放语音，不播放Loading。不使用有声“嗯……”、垫话或慢说；需要说明进度时使用简短文字。

若进入模式时已有语音或音效正在播放，应停止播放，记录信号到达、停播指令与实际停声边界，剩余必要内容改为文字。不为外部信号触发的停声伪造用户语音打断。

### 数据与时间线

助手回复保留在助手轨道，明确标记为文字片段，不关联音频或波形。文字片段的时间区间表示显示窗口，不表示语音时长；禁止用静音WAV冒充文字输出。表达控制轨道不为纯文字回复添加语音垫句或慢说标注。

非人工片段起点仍对齐400 ms；有因果依赖的跨轨道片段，前置结束后至少间隔400 ms。文本及模式信号的数据适配遵循[data.md](data.md)。

## 表达控制仅标记助手

表达控制轨道只标记助手表达行为，不对用户标记。垫句、慢说等标注必须关联助手片段；同段可分别标记。普通确认、常规语速、打断停播不自动添加表达标签。删除无信息量的“开始收听”“准备反馈”“查询完成”等重复占位块。

用户的慢说、停顿或其他说话特征，需要记录时使用当前契约支持的用户侧标注，不放入表达控制轨道。悄悄话模式进入记在世界轨道，文字回复记在助手轨道；不将纯文字片段标成语音慢说。
