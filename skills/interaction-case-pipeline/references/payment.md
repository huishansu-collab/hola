# 外卖与购物：支付确认与订单反馈

外卖、购物类 Case 在支付执行前必须展示确认支付卡片，由用户主动点击支付。口头同意不等于支付成功，助手不得代替用户支付。卡片包含商品、规格、数量、应付金额、收货地点及可用的预计送达信息，均依据当前工具结果，不补造。

本规则是“异步业务止于受理”的明确例外：外卖和购物覆盖支付确认，以及支付后一次订单状态查询和反馈；取得接单／订单确认结果时告知，仍待确认则如实结束于待确认状态。不延伸到备餐、配送或送达，不安排分钟级履约等待。支付等待由用户操作与外部回调决定，不套用工具受理时间窗口，不为赶在窗口内而伪造回调。

## 支付前语音引导

普通语音场景中，点击支付之前必须有助手实际播报，例如“一共十二块钱，点击一下卡片就好了”。不能仅以卡片文字代替语音。支付卡片先显示，展示片段结束后至少400 ms才开始引导；引导播完后至少400 ms才安排用户点击。新增这句台词时重生成助手完整母带并重新对齐，不从其他母带拼入单句。

明确启用纯文字模式时，遵循不发声约束；如任务同时要求支付语音，先说明冲突并请求澄清，不暗中省略必需语音或强行播放。

## 轨道与依赖

- 工具调用：创建待支付订单、显示支付卡片、查询订单状态、更新结果卡片。待支付订单不表示已付款或商家已接单。
- 用户控制：用户点击支付按钮；发送卡片不是用户控制动作。
- 世界信号：支付平台返回支付结果，关联当前订单。
- 后台判断：只依据已收到的支付和订单结果更新状态。

点击支付之后、回调之前可以留白，不添加占位判断，不提前标支付成功。收到成功回调后才能将支付状态设为成功；商家状态仍待查询。台词要求“点击卡片支付”前，卡片必须可见。支付后订单结果可用时，结果卡更新与不依赖屏幕可见的语音回答可并行。

## Few-shot：订一杯咖啡

场景前提：公司地址已确认；工具返回应付金额 20 元、预计送达约 25 分钟。以下业务数据均为模拟；25 分钟是展示的配送预计时间，不是 Case 等待时长。

1. 用户轨道：用户说“帮我订一杯咖啡。”
2. 工具调用与必要确认：查询商品、规格、价格、配送范围，确认必要选项；创建待支付订单，返回订单号、金额和预计送达时间。具体查询与建单工具按实际契约选用，字典未收录时先补充，不虚构已接入能力。
3. 工具调用：ui.show_card(...) 展示确认支付卡片，包含咖啡名称与规格、数量、20 元、公司地址、预计约 25 分钟送达、支付按钮。
4. 助手轨道：卡片显示结束至少400 ms后说“一共二十元，预计二十五分钟送到公司。确认没问题的话，点击卡片支付就可以了。”
5. 用户控制：上述语音结束至少400 ms后，用户点击卡片“支付”。
6. 等待支付回调：时间线留白，等待外部结果。
7. 世界轨道：支付平台回传支付成功，关联当前订单号。
8. 后台判断：支付已成功；商家是否接单仍待确认。
9. 工具调用：tools.check_order_status(order_id)，返回商家已接单、预计约 25 分钟送达。
10. 后台判断：根据结果确认商家接单，采用最新预计送达时间。
11. 工具调用与助手轨道并行：ui.show_card(...) 更新“商家已接单”与配送信息；助手说“店家接单了，预计二十五分钟后送到公司。”

## 分支

- 支付取消或失败：保留对应状态，不继续播报下单成功。
- 订单查询仍待接单：卡片和助手表达“已支付，等待商家接单”，不提前宣布接单。
- 购物类采用对应的“订单已确认”等真实或模拟返回状态，不机械套用“店家接单”。
- Case 到接单／订单确认反馈或当前待确认状态为止，不包含履约完成。

支付回调→后台判断→状态查询→结果判断→反馈，按每个前置片段结束后至少400 ms检查跨轨道依赖；独立的结果卡更新与语音可在各自满足窗口后并行。
