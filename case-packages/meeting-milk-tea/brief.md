# 需求：培训中低声点一杯奶茶

用户在公司参加培训，不方便出声，压着嗓子让助手点一杯瑞幸的茉莉花奶茶。
助手要在不打扰会场的前提下，把位置、地址、偏好和下单能力凑齐，跟用户对一遍，
建单，然后把付款这一步交还给用户。

## 要考察什么

1. **任务、品牌、商品是三件事**。任务是饮品下单，品牌是瑞幸，商品是用户原话里的
   「茉莉花奶茶」。不能因为归类成「订咖啡」就把商品改掉。
2. **能力先发现再使用**。`mcps.search` 拿到已连接、已授权的瑞幸下单能力之后，才谈报价和建单；
   不假定这个品牌的工具天生就在。
3. **偏好没记录就是没记录**。`memory.get(drink_preferences_key)` 返回 `not_recorded`，
   助手不编一个「你平时喝三分糖」出来。
4. **耳语不等于助手闭嘴**。用户耳语、场合安静，助手按已确认音色轻声承接，
   不播 Loading、不外放。真要纯文字，得有 Living Edge 双击那个世界信号，这条 Case 没有。
5. **口头确认覆盖到哪儿**。「是的」确认的是商品和地址，卡片可以据此自动确认；
   付款不在里面——助手把待支付卡片亮出来，请用户自己点。
6. **照返回值说话**。工具返回 `created_pending_payment`，助手就说下好了、多少钱、大概多久，
   不说「已付款」，也不说「商家已接单」。

## 边界与偏差

- 本 Case 止于**订单已创建、待支付，并引导用户点卡片付款**。点击、支付回调、
  商家接单查询不在里面。
- `references/payment.md` 要求外卖类 Case 一路走到「点击支付 → 支付回调 → 订单状态查询」。
  这条 Case 按需求方给的七步脚本收在建单和付款引导上，属于**有意收窄**：
  规则里「AI 不自动支付、口头同意不等于支付」这条守住了，后半段的点击与回调留给后续 Case。
- 工具与返回值全部为模拟数据（`simulated: true`），不构成任何真实下单授权。

## 时间

现在的时间是**按字数估的设计值**（`timing_status: planned`），配音之后按录音重排。
